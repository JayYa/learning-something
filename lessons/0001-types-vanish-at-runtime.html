类型只活在编译期

为什么一段 TypeScript 代码"能跑通"，却可能是错的？这课从语言设计与工具链的底层架构讲起，帮你建立审阅 AI 代码的第一套方法论：先查验证门禁，再看运行时边界，最后才看实现细节。

一、一个暴露真相的实验

你本机的 Node 是 v26，原生支持直接运行 .ts 文件。在讲任何理论之前，先用 5 分钟亲眼看一遍 TypeScript 的"分裂现场"。这个现象决定了你以后审阅所有 TS 项目时的第一直觉。

  1. 找一个空目录，新建 hello.ts。注意第 6 行故意把字符串 "1" 传给了要求 number 的参数：
    hello.ts
    function add(a: number, b: number): number {
  return a + b;
}

console.log(add(1, 2));
console.log(add("1", 2));
  2. 运行之前，先停 10 秒写下两个预测：
    ① node hello.ts 会报错拒绝运行，还是会打印结果？如果打印，第 2 行输出什么？
    ② 不加 --noEmit 直接运行 npx -p typescript tsc hello.ts，目录里会不会多出一个 hello.js？
    然后依次运行下面三条命令：
    Terminal
    node hello.ts
npx -p typescript tsc --noEmit hello.ts
npx -p typescript tsc hello.ts

你在本机看到的输出会是这样：

运行输出
> node hello.ts
3
12

> npx -p typescript tsc --noEmit hello.ts
hello.ts(6,17): error TS2345: Argument of type 'string' is not
assignable to parameter of type 'number'.

> npx -p typescript tsc hello.ts
hello.ts(6,17): error TS2345: Argument of type 'string' is not
assignable to parameter of type 'number'.

现在打开第三条命令产出的 hello.js，你会看到它竟然真的生成了，而且长这样：

hello.js（tsc 报错后仍然产出的文件）
function add(a, b) {
    return a + b;
}
console.log(add(1, 2));
console.log(add("1", 2));

同一个文件，发生了三件在 C# 世界里几乎不可想象的事：

  • 第一，node hello.ts 毫无警告地跑完了，而且不是崩溃，是安静地算出了一个错误答案 12。
  • 第二，tsc 明确报了类型错误，但在默认配置下仍然把 hello.js 写到了磁盘上（只是进程退出码不为 0）。
  • 第三，hello.js 里没有任何类型的痕迹，: number 像注释一样人间蒸发，剩下的代码完全按 JavaScript 的规则执行（+ 两边只要有一边是字符串，就做字符串拼接[MDN: 加法]）。

二、底层原因：为什么 TypeScript 必须"擦除类型"

如果只把上面的现象背成几条死规则，过两周就会忘，或者换个工具（比如 Vite、Next.js、tsx）就又懵了。要真正吃透，必须看清背后的四个底层设计原因。

1. 运行时约束：TS 没有自己的虚拟机，直接运行在 JS 引擎之上

在 C# 里，语言、编译器（Roslyn）、中间语言（IL）和运行时（CLR）是一整套垂直设计的体系。你写下的类型定义会被编译进程序集的元数据表，CLR 在运行时真的认识每一个类型，所以泛型参数可以保留到运行时（reified generics），typeof(T)、GetType() 和反射都顺理成章。

TypeScript 从诞生第一天起就不具备这个前提。它必须跑在现有的浏览器（V8、SpiderMonkey、JavaScriptCore）和 Node.js 上，不能要求全世界的 JS 引擎为它改架构，也不能给运行时增加额外开销。因此它选择了类型擦除（type erasure）：所有类型注解、interface、type 别名、泛型参数，全部只用于编译期静态分析，运行前统统剥离。[Handbook: Rethinking Types]

C#：单一耦合管道

.cs 源码 ↓ Roslyn（类型检查 + 生成 IL 强绑定） IL + 类型元数据（类型错误则无产物） ↓ CLR（运行时认识类型、支持反射） 执行结果

结论："能编出来并跑起来"几乎等价于"通过了类型检查"，而且运行时依然能依赖类型元数据。

TypeScript：两条独立管道

管道 A（验证）：.ts → tsc --noEmit → 报错 / 退出码 管道 B（执行）：.ts → 剥离类型 → 纯 .js → JS 引擎

结论：验证和执行默认是解耦的。管道 B 跑通，对管道 A 是否通过没有任何证明力。

2. 设计原则：类型系统不改变运行时行为

TypeScript 官方的《设计目标》里写着一条极其关键的非目标（Non-Goal）："不向程序添加或依赖运行时类型信息，也不根据类型系统的分析结果输出不同的运行时代码"（never emit different code based on the results of the type system）。[TypeScript Design Goals]

为什么要定下这条设计原则？背后有两个务实的工程原因：

  • 可预测性：开发者看着一行 TS 代码，只要在脑中把类型注解划掉，就能百分之百确定它在 JS 引擎里会怎么跑。你永远不用担心"编译器是不是根据某个隐晦的类型推导，偷偷帮我改写了运行时逻辑"。
  • 支持单文件极速转译：正因为输出 JS 不依赖跨文件的全局类型推导，外部工具才能只看单个文件的语法就把类型剥掉，不需要运行完整的类型检查器。

这条原则也顺带解释了 C# 开发者最容易困惑的几个"为什么 TS 做不到"：TS 不能像 C# 那样按参数类型做真正的运行时方法重载，不能在泛型函数里写 new T() 或 default(T)，interface 在编译后占用 0 字节。这些全都需要类型信息参与运行时。

3. 历史与渐进迁移：为什么 tsc 报错后默认仍输出 JS？

哪怕你用的是官方编译器 tsc，它在发现类型错误后默认依然会吐出 .js 文件，只通过非零退出码通知外部失败。这是 TS 团队有意保留的设计。[TypeScript #7602]

底层原因在于 TS 的核心定位是渐进式类型系统（gradual typing）：大量团队是把存量 JS 项目一点点改成 TS 的。如果一个文件里还有三处复杂类型没标好，编译器就彻底拒绝生成 JS，开发者连本地调试和跑单元测试都会被卡死。于是 TS 把"报错"和"阻止产出"拆开了：只有当你显式打开 noEmitOnError: true 时，它才会在出错时不产出文件。[TSConfig: noEmitOnError]

4. 现代工具链的架构分工：为什么 Node、Vite、esbuild 都"不检查类型"？

明白了前两条，你就能瞬间看穿整个现代前端与 Node 工具链的分工逻辑。把 TS 变成可执行的 JS，和检查 TS 的类型是否正确，其实是复杂度完全不同的两件事：

角色典型工具工作方式时间复杂度与速度做类型检查吗
类型剥离 / 转译器 node file.ts、Vite（esbuild）、SWC、Babel、tsx 逐文件扫描语法树，把类型注解删掉或换成空白 单文件线性处理，毫秒级 不做
静态类型检查器 tsc --noEmit、IDE 内置 TS 语言服务 读取 tsconfig.json，构建全项目模块依赖图与类型关系 全项目分析，秒级到数十秒 做

以你本机的 Node.js 为例：Node 运行 .ts 时采用的是类型剥离（type stripping），也就是把类型注解替换成等长的空白字符（这样甚至不需要 source map，报错堆栈的行号也能和源码严丝合缝）。官方文档明言 "no type checking is performed"。[Node.js: TypeScript] 同理，Vite 官方文档也专门强调："Vite only performs transpilation on .ts files and does NOT perform type checking."[Vite: TypeScript]

顺带一提：正因为 Node 只做纯粹的空白替换，像 enum、namespace 这种需要生成额外 JS 代码的 TS 专属语法，在默认 type stripping 模式下反而是不支持的。这也是为什么新版 TypeScript 专门引入了 erasableSyntaxOnly 选项，用来把项目限制在"纯可擦除语法"之内。[TSConfig: erasableSyntaxOnly]

5. 必须拆开的两套概念：TS 静态类型 ≠ JS 运行时类型

C# 开发者最容易混淆的一点是把"类型"当成一个整体。在 TS 项目里，你脑子里必须把两套完全不同的类型分开存放：

  • TS 静态类型（编译期契约）：附着在变量、参数、表达式上（例如 a: number、User、Promise<Order>）。它用来在代码运行前推理"这里可能出现什么值"，运行前全部消失。
  • JS 运行时类型（内存里的真实标签）：附着在具体的值上（例如 typeof x === "string"、Array.isArray(x)、x instanceof Error）。它永远存在，由 JS 引擎在运行时维护，但它根本不知道你当初给变量写过什么 TS 接口。

C# 的心智模型：编译期类型和运行时类型是同一张图纸的两面。string s 编译期是字符串，运行时 CLR 也保证它只能是字符串或 null；反序列化 JsonSerializer.Deserialize<User>(json) 会读取 User 的运行时元数据，按字段类型真正构造出对象。

TS 的心智模型：TS 类型只是编译期的"设计蓝图"，运行前就会被收走；JS 引擎只按内存里实际流进来的值干活。一旦你绕过了静态检查，或者数据从外部流进系统，变量名上贴着 : number 却装着一个字符串 "1"，在运行时完全合法，JS 引擎连眉头都不会皱一下。

三、方法论：用"双管道模型"审阅 AI 代码

理解了底层原因，我们把它们沉淀成三条可迁移的审阅方法论。以后无论 AI 给你写的是前端页面、Node 后端服务，还是自动化脚本，这套检查顺序都通用。

方法论原则 1 · Pipeline-First Review

先查门禁，再看代码：永远不要拿"跑通了"当"类型正确"

因为执行管道和验证管道是分离的，AI 告诉你"我跑了 node src/index.ts / npm run build，一切正常"，只证明 JS 语义下当前那条路径没崩，完全不能证明类型检查通过。

审阅动作：接手 AI 写的任何 TS 项目，先别急着读业务逻辑，第一眼先查三处：① package.json 的 scripts 里有没有独立的 typecheck（如 tsc --noEmit）；② build 命令是不是只跑了 vite build / esbuild 而漏掉了 tsc；③ CI 或提交前检查有没有真正执行类型检查并把非零退出码当作失败。没有门禁的项目，里面的所有类型注解都只是"随时可能过期的注释"。

方法论原则 2 · Static Interior, Validated Boundary

静态类型只守内部，所有运行时边界必须做运行时校验

既然 TS 类型在运行前归零，编译器能守住的只有程序内部，也就是从你自己的代码里创建并传递的值。凡是跨越运行时边界从外部进来的数据（例如 HTTP 接口返回值 await res.json()、JSON.parse()、环境变量 process.env、本地配置文件、用户输入），在编译期根本不存在，TS 不可能知道它们运行时的真实长相。

AI 最常见的坏习惯：在边界处直接写 const user: User = await res.json() 或 JSON.parse(raw) as Config。这看起来很像 C# 的强类型反序列化，实际上只是对编译器说"闭上眼睛相信我"，运行时零校验。

审阅动作：看到数据跨过外部边界，立刻问一句："如果上游少传了一个字段，或者把数字传成了字符串，这段代码会在入口处立刻报错，还是会把脏数据放进系统内部？" 答案如果是后者，就该要求 AI 在边界补上运行时检查（或使用校验库如 Zod，后续阶段会细讲）。

方法论原则 3 · Silent Corruption > Crash

最危险的不是崩溃，是 JS 弱类型导致的"静默错算"

在实验里，add("1", 2) 没有抛异常，而是算出了 12。这就是 JavaScript 隐式类型转换最阴险的地方：脏数据进来后，程序往往照跑不误，直到把错误金额写进数据库、把 "NaN" 展示给用户才暴露。

审阅动作：当 AI 试图用"我写了个测试跑通了"来打消你对类型报错的顾虑时，坚持你的判断：测试只能证明测到的那几组输入没出事；只有静态类型检查 + 边界运行时校验，才能守住没测到的分支和异常输入。

四、实战演练：按方法论审阅一段 AI 代码

假设你让 AI 写一个小脚本，从外部 JSON 字符串解析订单并计算总价。AI 交给你下面两个文件，并自信地回复："已用 node calc.ts 测试通过，输出正常。"

待审阅的 AI 交付物

package.json
{
  "name": "order-calc",
  "scripts": {
    "start": "node calc.ts",
    "build": "vite build"
  }
}
calc.ts
interface Order {
  price: number;
  shipping: number;
}

function loadOrder(raw: string): Order {
  return JSON.parse(raw) as Order;
}

function calcTotal(order: Order): number {
  return order.price + order.shipping;
}

const order = loadOrder('{"price": 100, "shipping": "10"}');
console.log(calcTotal(order)); // 运行时打印 "10010"，没有任何报错

按本课三条方法论逐层拆解：

  1. 查门禁（原则 1）：package.json 里只有 node calc.ts 和 vite build，两者都只剥离/转译、不做类型检查。这个仓库里根本没有类型门禁。
  2. 查边界（原则 2）：第 7 行 JSON.parse(raw) as Order 跨过了运行时边界。interface Order 在运行前已被擦除，as Order 只是让编译器闭嘴，运行时完全没有检查 shipping 到底是不是 number。
  3. 看后果（原则 3）：上游把 shipping 传成了字符串 "10"，代码既没在编译期报错，也没在运行时崩掉，而是静默拼出了 "10010"，这就是典型的静默数据污染。
"请做两处修改：① 在 package.json 中增加 typecheck: \"tsc --noEmit\"，并把 build 改为先跑 typecheck 再打包，同时附上 tsc --noEmit 的零报错输出；② loadOrder 是外部数据边界，不要用 as Order 直接断言，请在解析后对 price 和 shipping 做运行时类型校验（确认都是有限数字），不符合结构时显式抛出错误。"

注意上面这条指令为什么有效：它没有泛泛地说"写严谨点"，而是直接点中了门禁缺失和边界裸断言两个底层病根，AI 立刻知道该改哪里、怎么验收。

五、检验一下

每题只能选一次。凭理解与记忆作答，不要往上翻。

TypeScript 为什么把"不根据类型信息改变运行时产出代码"写进设计非目标？

  1. 为了强制所有项目必须开启严格检查模式
  2. 为了让擦除后保持标准且可预测的纯脚本
  3. 为了让虚拟机在运行时自动生成反射数据
  4. 为了在编译阶段自动重写所有低效的循环
不依赖类型来改写运行时行为，一方面保证把类型删掉后就是可预测的标准 JS，另一方面也让 Node、esbuild、Vite 这类工具能够做单文件极速转译，不必每次都跑全项目类型检查。

AI 交付项目里的构建命令只有 "build": "vite build"，且本地跑通了。这说明什么？

  1. 说明代码已经通过全量静态类型检查
  2. 说明项目关闭了所有运行时异常捕获
  3. 只说明语法转译成功但未必检查类型
  4. 只说明依赖包完整但尚未打包出产物
Vite（底层用 esbuild）只负责转译 .ts，默认不做类型检查。所以 vite build 成功不代表类型正确，必须确认有没有独立运行 tsc --noEmit。

AI 写了 const cfg = JSON.parse(text) as Config;。与 C# 的 JsonSerializer.Deserialize<Config>(text) 相比，最关键的区别是？

  1. 不会在运行时校验字段形状，脏数据会直接流入
  2. 会在运行时自动补全缺失字段，默认值设为零值
  3. 会在运行时抛出类型转换异常，阻止程序继续跑
  4. 会在编译期读取外部文件内容，提前验证其格式
C# 反序列化会依据运行时类型元数据校验并构造对象；TS 的 Config 和 as Config 在运行时全部被擦除，不会执行任何检查。外部数据边界必须自己做运行时校验。

默认配置下，对有类型错误的文件运行 tsc app.ts，结果会怎样？

  1. 不输出脚本文件，并且退出码为零
  2. 仍输出脚本文件，并且退出码为零
  3. 不输出脚本文件，并且退出码非零
  4. 仍输出脚本文件，并且退出码非零
为了支持从 JS 渐进迁移，tsc 把检查和产出解耦：出错时默认仍输出 .js，靠非零退出码通知 CI 失败。只有开启 noEmitOnError 才会在出错时阻止产出。

审阅泛型函数 function parse<T>(x: unknown) 时，AI 试图在函数体里通过反射读取 T 的字段列表。你应如何判断？

  1. 可以实现，只要开启实验性的反射编译选项
  2. 无法实现，泛型参数在运行前已被彻底擦除
  3. 可以实现，但必须把函数改成类方法才有效
  4. 无法实现，因为脚本引擎不支持任何泛型值
TS 没有 CLR 那样的运行时泛型实体化（reification），泛型参数 T 只存在于编译期，运行前被彻底擦除。想在运行时校验结构，只能显式传入校验函数或 schema 对象。

接手一个 AI 刚生成的 TypeScript 仓库，按本课方法论，你最应该先做哪一步？

  1. 逐行检查所有变量命名是否符合团队规范
  2. 先把全部接口改写成类以便做运行时反射
  3. 先查脚本与流水线里有没有跑静态检查器
  4. 直接运行主入口文件看是否抛出运行异常
遵循"先查门禁，再看代码"（Pipeline-First Review）：如果 package.json 和 CI 里根本没跑 tsc --noEmit，代码里再多类型注解也没有把关机制。
