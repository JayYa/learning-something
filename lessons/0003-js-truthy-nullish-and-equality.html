JS 的空值、真假值与判等

TypeScript 的类型在运行前会被擦除，真正跑在引擎里的是 JavaScript 的求值规则。这课从 null 与 undefined、真假值转换、|| 与 ?? / ?.、以及 == 与 === 讲起，帮你识别 AI 代码里最常见的静默逻辑错误。

一、一个 5 分钟实验：让 Node 暴露 JS 的反直觉求值

在 C# 里，if 括号里必须是 bool，null 只有一种，0 绝不会被当成"没有值"。JavaScript 则完全不同。先用本机的 Node 跑 6 行代码，亲眼确认这些差异。

  1. 新建 js-values-demo.ts，粘贴下面代码：
    js-values-demo.ts
    const cfg = { timeout: 0, retries: undefined, label: "" };
console.log("1:", cfg.timeout || 3000, "|", cfg.timeout ?? 3000);
console.log("2:", JSON.stringify(cfg.label || "default"), "|", JSON.stringify(cfg.label ?? "default"));
console.log("3:", Boolean([]), Boolean({}), Boolean("0"));
console.log("4:", 0 == "", "" == false, 0 === "");
console.log("5:", NaN === NaN, isNaN("abc"), Number.isNaN("abc"));
console.log("6:", JSON.stringify({ a: undefined, b: null }));
  2. 运行前先停 15 秒写下三个预测：
    ① 第 2 行里，cfg.timeout 是合法的数字 0，|| 3000 和 ?? 3000 输出一样吗？
    ② 第 4 行里，空数组 []、空对象 {}、字符串 "0" 转成布尔值分别是 true 还是 false？
    ③ 第 7 行把包含 undefined 和 null 的对象序列化成 JSON 后，两个键都会保留下来吗？
    运行 node js-values-demo.ts，观察输出：
    运行输出（Node v26）

2: "default" | ""

4: true true false
5: false true false

这 6 行输出几乎浓缩了 C# 开发者初读 JS/TS 代码时最容易踩的所有运行时坑：0 和 "" 被 || 静默吞掉了；空数组和空对象在条件判断里都是真值；0 == "" 居然成立；NaN 不等于它自己；undefined 在 JSON 序列化时直接消失了。

二、底层原因：为什么 JavaScript 会这样表现？

这些行为不是零散的怪癖，而是由 JavaScript 运行时规范里的四套基础机制决定的。理解了机制，你在审阅任何 AI 生成的条件判断和表达式时都能一眼看出隐患。

1. 为什么 JS 有两个"空"：undefined 与 null

在 C# 里，引用类型没有对象就是 null（值类型加 ? 表示可空）。JavaScript 从 1995 年第一版设计时就并存着两个"空值"：

  • undefined（未定义 / 缺失）：由 JS 引擎在"没有值"的地方自动产生。声明了变量未赋值、访问对象上不存在的属性、函数没有 return、调用函数时漏传参数，拿到的全都是 undefined。[MDN: undefined]
  • null（明确为空）：引擎几乎不会自动产生 null，它通常由开发者或后端接口显式赋值，用来表达"这里存在这个字段，但当前明确没有值"。[MDN: null]

两者在工程审阅中最容易引发 bug 的两个运行时差异：

  • JSON 序列化行为不同：JSON.stringify({ a: undefined, b: null }) 的结果是 {"b":null}，值为 undefined 的键会被直接省略。在 PATCH 更新接口中，很多后端把"不传该键"理解为"保持原值"，把"传 null"理解为"清空字段"。如果 AI 把清空逻辑错写成 undefined，接口会静默失效。
  • typeof null === "object" 的历史遗留：这是 JS 第一版实现留下的类型标签 bug，因兼容海量存量网页永远无法修复。审阅类型守卫代码时，看到 if (typeof x === "object") 却没补一句 x !== null，后面访问 x.id 就会在遇到 null 时直接抛出 TypeError。[MDN: typeof]

2. ToBoolean 与真假值表：为什么 if (x) 什么都能放进去

C# 在编译期强制要求 if (...) 的条件必须是 bool。JavaScript 作为动态脚本语言，允许任意值出现在条件位置（if (x)、while (x)、!x、x ? a : b、a && b、a || b），引擎会自动调用规范里的抽象操作 ToBoolean 把它转成真或假。

好消息是，整个 JavaScript 世界里假值（Falsy）只有固定的 8 个，除此之外的一切值全都是真值（Truthy）：[MDN: Falsy]

分类具体值审阅时的常见陷阱
8 个假值（Falsy） false、0、-0、0n（BigInt 零）、""（空字符串）、null、undefined、NaN 0、""、false 在业务里往往是完全合法的输入值（例如免费价格 0、第 0 页、空备注 ""、开关 false），不能当成"没传值"。
容易误判的真值（Truthy） []（空数组）、{}（空对象）、"0"（字符串零）、"false"（非空字符串） AI 写 if (items) 想判断"列表非空"，结果接口返回 [] 时条件照样为真；正确写法必须显式检查 items.length > 0。

3. ||、&&、?? 与 ?.：逻辑运算符返回的不是布尔值

C# 开发者读 JS 代码时，最容易看晕的往往是满屏的 a || b、a && b、a?.b ?? c。先记住一条底层规则：JS 的 ||、&&、?? 并不返回布尔值，它们返回的是实际决定短路结果的那一侧操作数本身。

逻辑或：a || b（按真假值判断）

求值 a → ToBoolean(a) 为 true ? 是 → 直接返回 a（不求值 b） 否 → 求值并返回 b

问题：当 a 是 0、"" 或 false 时，ToBoolean(a) 为 false，会被误判为"无效"而回退到 b。

空值合并：a ?? b（只按 nullish 判断）

求值 a → a 是 null 或 undefined ? 是 → 求值并返回 b 否 → 直接返回 a（0、""、false 都会保留）

定位：ES2020 专门为"设置默认值"引入的运算符，语义精准对齐 C# 的 ??。[MDN: ??]

再看配套出现的另外两个高频写法：

  • 逻辑与 a && b：如果 a 为假值，直接返回 a；如果 a 为真值，则求值并返回 b。AI 经常用它写条件执行（如 isDebug && logDetail()）或前端条件渲染。注意隐患：如果左侧是数字 0（例如 items.length && renderList()），表达式会直接返回数字 0 而不是 false。
  • 可选链 ?.：支持属性访问 a?.b、动态键/数组下标 a?.[key]、以及函数调用 cb?.(arg)。只要 ?. 左侧是 null 或 undefined，整条后续访问链立刻短路，统一返回 undefined（即使左侧是 null，结果也是 undefined），不会抛 TypeError。[MDN: ?.]

C# 的心智模型：&& 与 || 只能连接 bool 且只返回 bool；给空值设默认值天然就用 ??；空条件访问用 ?.（支持 a?.b、a?[0]、fn?.Invoke()），且 null?.Prop 返回对应可空类型的 null。

JS / TS 的心智模型：&& 与 || 可以连接任意类型并返回原始操作数；早年 JS 没有 ??，历史代码和部分 AI 训练语料习惯用 || 写默认值，导致 0 / "" / false 被误杀。现代 TS 代码里，设默认值应默认使用 ??，配合可选链写成 user?.profile?.name ?? "匿名"。注意 JS 动态索引与函数调用必须保留点号：arr?.[0]、fn?.()。

4. 宽松相等 == vs 严格相等 ===，以及 NaN 陷阱

JavaScript 提供多套相等比较算法，审阅代码时必须分清它们在类型不同时的行为：[MDN: 相等比较与相同性]

写法规范算法跨类型时怎么处理典型结果与审阅建议
a === b / a !== b IsStrictlyEqual 不做转换，类型不同直接返回 false 0 === "" 为 false；null === undefined 为 false；默认首选。
a == b / a != b IsLooselyEqual 先按复杂规则做隐式类型转换再比较 0 == ""、"" == false、"0" == false、[] == false 全为 true，且不满足传递性（0 == "" 且 0 == "0"，但 "" == "0" 为 false）；默认禁用。
Object.is(a, b) SameValue 不做转换，修复 === 的两个 IEEE 754 边界 Object.is(NaN, NaN) 为 true，Object.is(+0, -0) 为 false；主要用于需要区分 NaN 的底层比较。

关于 NaN（Not-a-Number）：按照 IEEE 754 浮点数标准，NaN === NaN 恒为 false，所以写 if (x === NaN) 永远进不去分支。同时要警惕两个长得很像的函数：

  • 全局 isNaN(x)（慎用）：会先把参数隐式转成数字再判断。于是 isNaN("abc") 返回 true，但 isNaN("")、isNaN(null)、isNaN(false) 因为能转成 0 而全部返回 false。[MDN: isNaN]
  • Number.isNaN(x)（推荐）：不做隐式转换，只有当 x 本身是数字类型且值为 NaN 时才返回 true。如果审阅数值输入边界，更常见也更安全的做法是直接用 Number.isFinite(x)，一次性排除非数字、NaN 以及 Infinity。[MDN: Number.isNaN]
业界分歧（x == null 例外）：在所有 == 的用法里，只有 x == null（与 x != null）在 JS/TS 社区存在明确分歧。因为规范里 null 和 undefined 彼此宽松相等且不等于其他任何值，所以 x == null 恰好等价于 x === null || x === undefined。一派团队（包括不少知名开源库）认为它简短清晰且 TypeScript 编译器也原生支持它做类型收窄；另一派团队通过 ESLint eqeqeq 规则全仓禁用 ==，要求显式写出 x === null || x === undefined 或改用 ??，避免团队成员误把 == 用到其他类型上。审阅时以项目既有规范为准，不要在同一仓库里混用两种风格。

三、方法论：审阅 JS 条件与表达式的三条规则

结合第 0 阶段建立的审阅习惯，把今天这课的运行时机制压缩成三条可直接复用的检查动作。

方法论原则 7 · Nullish Over Falsy

默认值认准 ??，见到 || 先拷问 0、"" 和 false

AI 写默认值时经常习惯性冒出 a || fallback。只要字段可能是数字、字符串或布尔值，|| 就会把合法的边界值静默覆盖掉，且编译器不会报任何错误。

审阅动作：在代码里扫到 || 赋默认值，立刻套三个测试值心算一遍：如果左侧是 0、"" 或 false，业务上到底应该保留它还是回退到默认值？只要应该保留，立刻要求 AI 把 || 改成 ??；如果扫到 if (arr) 判断数组或对象是否为空，要求改为 arr.length > 0。

方法论原则 8 · Strict Equality, Safe NaN

判等一律要求 ===，数值边界认准 Number.isFinite / Number.isNaN

TS 的静态类型检查在变量已知为不同类型时会拦截部分 ==，但一旦遇到 any、unknown 或外部运行时脏数据，== 就会悄悄触发隐式转换（比如 "" == 0 变成 true）。

审阅动作：看到 == 或 !=，除非项目明确约定允许 x == null，否则一律要求改为 === / !==；看到全局 isNaN(x) 或 x === NaN，要求改为显式转换加 Number.isNaN(n) 或直接用 Number.isFinite(n)。

方法论原则 9 · Read Expressions by Return Value

按"返回哪一侧操作数"读逻辑表达式，并盯紧 undefined 与 null 的序列化差异

不要用 C#"逻辑运算返回布尔值"的直觉去读 JS 的 && / || / ?.。同时在对接外部 JSON API 时，始终记得 undefined 会被 JSON.stringify 静默丢弃，而 null 会被保留。

审阅动作：读到链式写法（如 a?.b?.[0] ?? c 或 flag && expr），逐段翻译成"左侧是空/假时返回什么，否则返回什么"；审阅 PATCH/更新类请求体时，专门确认需要清空的字段传入的是 null 还是不小心传了 undefined。

四、实战演练：审阅一段 AI 写的查询与折扣处理代码

假设你让 AI 写一个解析查询参数并构造更新请求的函数。AI 提交了下面这段代码，且 tsc --noEmit 竟然通过了（零报错），因为这些全是运行时逻辑陷阱：

待审阅的 AI 交付物

query-helper.ts
interface QueryInput {
  page?: number;
  discount?: number;
  tags?: string[];
  total: number;
  count: number;
  clearNote?: boolean;
}

function normalizeQuery(input: QueryInput | null) {
  if (typeof input !== "object") {
    throw new Error("输入必须是对象");
  }

  const page = input?.page || 1;
  const discount = input?.discount || 10;

  if (input?.tags) {
    console.log("按标签过滤:", input.tags.join(","));
  }

  const avg = (input?.total ?? 0) / (input?.count ?? 0);
  if (Number.isNaN(avg)) {
    throw new Error("平均值非法");
  }

  return JSON.stringify({
    page,
    discount,
    avg,
    note: input?.clearNote ? undefined : "keep",
  });
}

按本课三条原则逐行拆解（全部可以通过 tsc --noEmit，但运行时都会出问题）：

  1. 第 11 行（typeof null 陷阱）：函数接受 QueryInput | null，但 typeof null === "object"，所以传入 null 时不会抛错。正因为没拦住 null，AI 才不得不在后面到处加 input?.（用第 2 课的悬停检查第 15 行的 input，你会发现它依然是 QueryInput | null）。正确写法必须改为 if (typeof input !== "object" || input === null)。
  2. 第 15、16 行（原则 7）：input?.page || 1 和 input?.discount || 10 用了 ||。如果业务允许第 0 页或 0 折扣，0 会被当成假值静默覆盖成 1 和 10，必须改为 ??。
  3. 第 18 行（原则 7）：if (input?.tags) 想判断"有没有传过滤标签"，但如果调用方传了空数组 []，空数组是真值，分支照样执行并打印空字符串。应改为检查 (input.tags?.length ?? 0) > 0。
  4. 第 23 行（原则 8）：当 total 为 100、count 为 0 时，除法结果是 Infinity 而非 NaN，Number.isNaN(Infinity) 返回 false，导致校验被绕过（且 JSON.stringify 会把 Infinity 静默序列化成 null）。应改为 !Number.isFinite(avg)。
  5. 第 31 行（原则 9）：当 clearNote 为 true 时，代码给 note 赋了 undefined。经过 JSON.stringify 后 note 键会直接从 JSON 里消失，后端收不到清空意图。明确表达"清空字段"应赋值为 null。
"这段代码虽然过了 tsc --noEmit，但存在五处 JS 运行时逻辑问题，请一并修改：① 第 11 行补上 input === null，真正拦住 null 并去掉后续多余的 input?.；② 第 15、16 行的默认值改用 ??，避免合法的 0 被 || 覆盖；③ 第 18 行改为检查 (input.tags?.length ?? 0) > 0，不要把空数组 [] 当成有过滤条件；④ 第 23 行改为 !Number.isFinite(avg)，同时拦住 NaN 和除以零产生的 Infinity；⑤ 第 31 行清空备注时把 undefined 改为 null，避免 JSON.stringify 丢弃该字段。"

五、检验一下

本课自测（接续开头的 2 道热身题，全页共 8 题）。每题只能选一次，凭理解作答，不要往上翻。

AI 写了 const timeout = cfg.timeout || 3000; 来给超时时间设默认值。当用户明确传入 timeout: 0（表示不限时）时，运行时会发生什么？

  1. 保留零值，逻辑或只在空值与未定义时回退
  2. 抛出异常，逻辑或要求左侧必须是布尔类型
  3. 变成三千，数字零属于假值会被右侧值覆盖
  4. 返回假值，逻辑或的运算结果固定是布尔值
|| 按真假值判断，数字 0 是 8 个假值之一，因此 0 || 3000 会静默返回 3000。给数字、字符串或布尔字段设默认值必须用空值合并运算符 ??。

审阅代码时看到 if (items) { process(items); }，其中 items 是接口返回的数组。当接口返回空数组 [] 时，这段逻辑会怎么走？

  1. 仍会进入分支，空数组在条件里属于真值
  2. 会跳过该分支，空数组在条件里属于假值
  3. 编译阶段报错，条件表达式只接受布尔值
  4. 运行阶段报错，数组无法隐式转成布尔值
JavaScript 中只有 8 个假值（false、0、-0、0n、""、null、undefined、NaN）。空数组 [] 和空对象 {} 都属于对象引用，转布尔值恒为 true。判断数组非空应检查 items.length > 0。

下面哪段表达式在 user 为 null 时能安全回退到 "匿名"，同时在 user.name 为空字符串 "" 时保留空字符串？

  1. user?.name || "匿名"
  2. user?.name ?? "匿名"
  3. user.name ?? "匿名"
  4. user?.name && "匿名"
user?.name 在 user 为 null 时安全短路为 undefined，再由 ?? 回退到 "匿名"；当 user.name 是 "" 时，它既不是 null 也不是 undefined，所以 ?? 会完整保留 ""。

审阅 AI 写的条件判断 if (code == 0)，如果外部输入 code 意外传入了空字符串 ""，运行时结果是什么？

  1. 条件为假，宽松相等会先校验两侧类型是否一致
  2. 运行报错，不同类型的值禁止参与宽松相等比较
  3. 条件为假，空字符串只与未定义和空值宽松相等
  4. 条件为真，宽松相等会把空字符串隐式转成数字
==（宽松相等）在比较字符串与数字时，会把字符串隐式转换为数字，空字符串 "" 转为 0，导致 "" == 0 为 true。审阅时应统一要求使用严格相等 ===。

AI 用 if (isNaN(input)) 检查外部输入是否为非法数字。为什么审阅时通常建议改用 Number.isNaN 或 Number.isFinite？

  1. 全局版本会先强转数字，非数字字符串易引发误判
  2. 全局版本无法识别非数，遇到浮点溢出恒返回假值
  3. 全局版本仅限浏览器端，在服务端运行会抛出异常
  4. 全局版本会改写原变量，导致后续的数值计算出错
全局 isNaN(x) 会先对参数做隐式数字转换：isNaN("abc") 返回 true，而 isNaN("")、isNaN(null) 返回 false。Number.isNaN(x) 不做隐式转换，Number.isFinite(x) 则可同时排除非数字、NaN 与无穷大。

后端接口约定字段 discount 传 null 表示"清空折扣"，不传该键表示"保持不变"。AI 组装请求体时写了 { id: 1, discount: undefined } 并用 JSON.stringify 发送。结果会怎样？

  1. 序列化后保留该键，值会被自动转换成空值标记
  2. 序列化时抛出异常，协议不允许出现未定义字段
  3. 序列化时丢弃该键，后端会误判成保持原有折扣
  4. 序列化后保留该键，值会被转换成空字符串发出
JSON.stringify 会直接忽略值为 undefined 的对象属性，最终发出的只是 {"id":1}。想明确向后端传递空值必须使用 null。
