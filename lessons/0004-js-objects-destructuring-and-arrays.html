对象、解构展开与数组链式操作

AI 写的 TypeScript 里，出现频率最高的不是类继承，而是对象字面量、解构与展开（...），以及 map / filter / reduce / sort 数组链。这课讲清它们的运行时语义和 C# 差异，并明确标出哪些问题 tsc 根本不会报错。

零、课前热身：回顾前面课程

不翻前面的课程，先用 2 道题唤起记忆（这两题会计入页底的总分）。

审阅 AI 写的数据校验逻辑时，看到 if (isNaN(raw)) 用来拦截非法数字输入。为什么更建议改成显式转换配合 Number.isFinite？

  1. 全局版本无法判断非数，遇到计算溢出固定返回真值
  2. 全局版本在服务端失效，只在浏览器环境里正常运行
  3. 全局版本会先强转数字，空串与空值都会被当成合法
  4. 全局版本会改写原变量，导致后续读取出现类型错误
全局 isNaN(x) 会先调用 Number(x) 强转，导致 ""、" "、null、false 转成 0 而返回 false，校验被直接绕过。先显式处理空串并转换，再用 Number.isFinite(n) 可同时排除非数字、NaN 与 Infinity。

AI 写了一个函数 function loadCfg(s: string): Cfg { return JSON.parse(s) as Cfg; }，且 tsc --noEmit 零报错。审阅时该怎么判断？

  1. 存在风险，运行时无结构校验，脏数据会绕过类型层
  2. 完全安全，显式返回类型会自动触发运行时字段检查
  3. 存在风险，编译器会把裸断言转成异常导致启动崩溃
  4. 完全安全，标准解析函数会依据目标接口过滤掉脏键
TypeScript 类型在运行前会被全部擦除。即使函数写了显式返回类型，内部对外部 JSON 直接用 as Cfg 裸断言仍然没有任何运行时校验，缺字段或错类型的脏数据会直接流入后续逻辑。

一、一个 5 分钟实验：让 Node 暴露对象与数组的四类静默坑

在 C# 里，LINQ 的 OrderBy / Where / Select 绝不会修改原集合，对象的属性修改边界也比较清晰。JavaScript 的对象展开与数组方法看着很像语法糖，但藏着几个 tsc 不会拦的运行时行为。先用本机 Node 跑一小段代码确认一下。

  1. 新建 js-objects-arrays-demo.ts，粘贴下面代码：

const copy = { ...base };
copy.env = "dev";
copy.retry.max = 99;
console.log("1:", base.env, base.retry.max);

const { page = 1, tag = "all" } = { page: undefined, tag: null };
console.log("2:", page, tag);

console.log("3:", nums, sorted === nums);

const items = [1, 2, 3];

const good = items.map(n => ({ id: n }));
console.log("4:", bad, good);
  2. 运行前先停 15 秒写下三个预测：
    ① 第 5 行里，改完 copy.env 和 copy.retry.max 之后，原对象 base.env 和 base.retry.max 分别是什么？
    ② 第 8 行里，解构默认值 tag = "all" 遇到 tag: null 时，会生效吗？
    ③ 第 12 行里，nums.sort() 之后原数组 nums 变了吗？排列顺序是 [1, 2, 10] 还是别的？
    运行 node js-objects-arrays-demo.ts，观察输出：

2: 1 null

4: [ undefined, undefined, undefined ] [ { id: 1 }, { id: 2 }, { id: 3 } ]
先分清 TS 管不管：上面 4 组结果里，第 1 组（浅拷贝污染原对象）、第 2 组（解构默认值不拦截 null）、第 3 组（sort() 原地改数组且按字符串排序），在 tsc --noEmit 严格模式下全部零报错。只有第 4 组的 n => { id: n } 在严格配置下可能触发"未使用标签"提示，但换成带 if 分支的 map 时 tsc 照样放行。也就是说，这四类行为在审阅 TS 代码时都必须靠眼睛盯住。

二、底层原因：对象、解构与数组方法是怎么工作的？

理解这四套底层机制，你读 AI 写的数据变换代码时，就能直接看穿数据流有没有被意外污染、顺序对不对、边界空不空。

1. 对象字面量、展开（Spread）与浅拷贝边界

在 C# 里，定义数据结构通常先建 class 或 record 再 new。JavaScript 的普通对象本质上是一个动态键值对字典（哈希表），随时可以用花括号字面量直接拼出来，并且支持几种 AI 极常用的简写：

  • 属性简写：当变量名和属性名相同时，{ env, limit } 等价于 { env: env, limit: limit }。
  • 计算属性名：键名如果是动态变量，用方括号包起来：{ [fieldName]: value }。如果漏了方括号写成 { fieldName: value }，键名就会变成字面字符串 "fieldName"。
  • 对象展开 { ...a, ...b }：底层做法是遍历源对象自身的可枚举属性，按顺序逐个赋值到新对象上。[MDN: 展开语法]

因为展开只是按顶层键逐个赋值，它天然带来两条运行时规则：

规则 A：展开永远是浅拷贝（Shallow Copy）

base = { env: "prod", retry: <ref #1> } copy = { ...base } copy = { env: "prod", retry: <ref #1> } // 同一引用

基本类型字段（字符串、数字、布尔）按值复制，互不影响；但嵌套对象或数组字段只复制了引用地址。改 copy.retry.max 就是在改 base.retry.max。

规则 B：靠后的键覆盖靠前的键（Order Wins）

{ ...defaults, ...override } // 正确：覆盖项在后 { ...override, ...defaults } // 错：默认值冲掉覆盖项 { ...input, role: "user" } // 安全：固定字段放最后

同名属性出现多次时，永远以后出现的为准。注意如果后一个对象里显式存在 { limit: undefined }，它同样会把前面已有的 limit: 10 覆盖成 undefined。

当确实需要修改嵌套属性又不能污染原对象时，工程上有两种清晰写法：如果只改其中一层嵌套，显式逐层展开 { ...base, retry: { ...base.retry, max: 5 } }；如果是多层未知深度的纯数据对象，直接用现代 JS 原生提供的全局函数 structuredClone(base) 做深拷贝（Node 17+ 与所有现代浏览器内置，注意它不能拷贝函数和 DOM 节点）。[MDN: structuredClone]

C# 的心智模型：C# 9 的 record 提供的 base with { Env = "dev" } 表达式，以及 Object.MemberwiseClone()，在语义上和 JS 的 { ...base, env: "dev" } 几乎一致：都是浅拷贝，嵌套引用类型依然共享同一个对象实例。

差异在于频度与隐蔽性：C# 里只有 record 才能用 with，且嵌套结构常配合不可变集合；JS 里任何对象和数组都能随手 { ...x } 和 [...arr]，AI 非常喜欢用它来"避免修改原对象"，却经常忘记第二层嵌套还是共享引用。

2. 解构赋值（Destructuring）与剩余收集（Rest）

解构赋值是从对象或数组里把字段批量拆到局部变量的语法，AI 在函数参数和返回值处理里几乎每十行就用一次：[MDN: 解构赋值]

destructuring-patterns.ts
// 1. 对象解构：按属性名匹配，支持重命名（原名: 新变量名）和默认值
const { id: userId, page = 1, ...otherFields } = payload;

// 2. 数组解构：按位置下标匹配，支持收集剩余元素
const [first, second, ...restItems] = list;

// 3. 函数参数解构：审阅签名时极常见，注意 "= {}" 防止调用方不传参时崩掉
function fetchUsers({ limit = 20, offset = 0 }: { limit?: number; offset?: number } = {}) {
  return { limit, offset };
}

读解构代码时，最容易看错的三处细节：

  • 冒号 : 在解构里是"重命名"，不是类型注解：在 const { id: userId } = user 里，id 是原对象属性名，userId 才是新定义的局部变量名。真正给整个解构加 TS 类型注解要写在花括号外面：function f({ id }: User)。
  • 同样是 ...，位置不同语义相反：出现在等号左边或函数形参里叫 Rest（剩余收集），把没被拆走的其余字段打包成一个新对象/新数组（同样是浅拷贝）；出现在等号右边、字面量或实参里叫 Spread（展开），把已有对象/数组拆开铺平。
  • 解构默认值只认 undefined：这和第 3 课的 ?? 不同。?? 会同时拦截 null 和 undefined，但解构里的 = 默认值 只在对应属性严格等于 undefined（或缺失）时触发；如果接口返回了 { tag: null }，解构出来的 tag 依然是 null。

3. 数组链式方法与 C# LINQ 深度对照

C# 开发者读 JS 数组链最舒服的地方在于，绝大多数高频方法都能直接和 LINQ 一一对应：

JS 数组方法C# LINQ 对应作用与返回值修改原数组吗
arr.map(fn) [MDN]Select逐项映射，返回等长新数组否
arr.filter(fn) [MDN]Where按条件筛选，返回满足条件的新数组否
arr.reduce(fn, init) [MDN]Aggregate把数组归约为单个值（数字、对象、Map 等）否
arr.flatMap(fn) [MDN]SelectMany先映射再展平一层，常用来一次完成"过滤 + 变换"否
arr.find(fn)FirstOrDefault返回首个满足条件的元素，找不到返回 undefined否
arr.some(fn) / every(fn)Any / All短路判断是否存在 / 全部满足，返回 boolean否
arr.sort(cmp) [MDN]List.Sort（非 LINQ）原地排序并返回原数组引用，默认按 UTF-16 字符串排会！
arr.toSorted(cmp) [MDN]OrderBy(...).ToList()ES2023 非破坏性排序，返回排好序的新数组否

C# LINQ 的底层机制（延迟求值）：list.Where(...).Select(...) 只是组装了一个状态机迭代器（IEnumerable<T>），不会立刻遍历，也不会分配中间数组。直到调用 .ToList() 或 foreach 时才单趟流式执行，因此需要小心"多次枚举同一查询"。

JS 数组链的底层机制（急切求值）：每调用一次 .filter() 或 .map()，引擎都会立刻完整遍历一次并分配一个新数组。日常几百几千条数据可读性优先，完全没问题；但在大数据量或高频循环里连写四五层链式调用会产生大量临时数组，此时合并成 flatMap 或单个 for...of 循环更干净。

4. 数组操作里最常坑人的四个细节

  • 原地修改（Mutating） vs 返回新数组（Non-mutating）：JS 早期数组 API 的一大设计割裂是部分方法会直接改原数组，且返回值依然是原数组引用，看着像链式调用，实际上把调用方传进来的入参给污染了。审阅时重点盯紧这几个原地修改方法及其 ES2023 安全替代品：
    会修改原数组（慎用）返回新数组的安全替代（ES2023 / 展开）常见坑
    arr.sort(cmp)arr.toSorted(cmp) 或 [...arr].sort(cmp)污染入参顺序；不传比较器时按字符串字典序排（[10, 2, 1] 变 [1, 10, 2]）
    arr.reverse()arr.toReversed() 或 [...arr].reverse()以为拿到了反转副本，结果把原列表也倒过来了
    arr.splice(i, count)arr.toSpliced(i, count) 或 arr.slice(...)名字和 slice 只差一个字母，splice 原地删改，slice 才返回切片副本
    arr.push(x) / arr[i] = x[...arr, x] / arr.with(i, x)在前端状态管理或共享缓存里直接原地修改，导致引用未变、变更检测失效
  • reduce 漏传第二个参数（初始值）：arr.reduce((acc, cur) => ..., initialValue) 如果省掉 initialValue，引擎会拿数组第 0 个元素当初始累加器，从第 1 个元素开始算。这有两个严重后果：第一，数组为空 [] 时直接抛 TypeError: Reduce of empty array with no initial value；第二，当数组元素是对象而你想求和数字时，首项是对象导致类型直接错乱。
  • 箭头函数返回对象字面量漏括号：JS 语法规定箭头函数右侧紧跟 { 时优先解析为函数体代码块，所以 u => { id: u.id } 里的 id: 被当成了一个跳转标签，函数没有 return，结果全是 undefined。简写返回对象必须加圆括号：u => ({ id: u.id })。
  • 在 map 里做条件 if 筛选：map 的契约是"输入 N 个元素，输出 N 个元素"。如果在 map 回调里只写 if (x.ok) return x.name;，不满足条件的分支会隐式返回 undefined，数组里就混进了洞。想既筛选又映射，写 .filter(...).map(...) 或 .flatMap(x => x.ok ? [x.name] : [])。
业界分歧（for...of vs reduce 写复杂聚合）：简单的数组求和（如 nums.reduce((s, n) => s + n, 0)）大家普遍接受 reduce；但遇到按字段分组、构造嵌套对象、或者需要中途 break 的复杂逻辑时，社区存在明显分歧。一派偏爱函数式链式写法，连对象分组也用 reduce（甚至在 reduce 里写 { ...acc, [k]: v }，把原本 O(n) 的循环硬生生写成 O(n²) 的重复拷贝）；另一派认为复杂的 reduce 极难阅读和调试，主张直接写清晰直白的 for...of 循环，或使用现代内置方法 Object.groupBy / Map.groupBy。审阅 AI 代码时，如果一段 reduce 超过 5 行、或在累加器里反复展开 { ...acc }，完全有理由要求 AI 改成 for...of 循环。

三、方法论：审阅对象与数组操作的三条规则

接续第 3 课的三条原则，把今天的对象、解构与数组机制压缩成三条可直接复用的审阅动作。

方法论原则 10 · Spread Is Shallow, Order Wins

见到 { ...obj } 立刻问两件事：有嵌套写入吗？覆盖顺序反了吗？

对象展开只做浅拷贝，且同名键以靠后的为准。AI 经常用 { ...defaults } 试图保护全局默认配置，却在下一行直接改了嵌套对象的字段；或者把 defaults 写在了 override 后面，导致配置覆盖静默失效。

审阅动作：凡是复制全局常量、状态对象或函数入参后要修改嵌套属性，要求逐层展开或改用 structuredClone；凡是合并默认值与外部覆盖项，确认顺序一定是 { ...defaults, ...override }，安全锁定字段放在最末尾；见到解构赋默认值，再核对一眼该字段是否可能收到 null（会绕过默认值）。

方法论原则 11 · Mutating vs Non-Mutating

见到 sort / reverse / splice 先查是否污染入参，数字排序必查比较器

这几个方法在 tsc 里不会报任何错，但会悄悄篡改调用方传进来的数组，引发难以排查的远距离副作用；而 sort() 漏传比较器会把数字按字符串排错。

审阅动作：审阅函数体里对参数数组的操作，看到 sort、reverse、splice 立刻要求改为 toSorted、toReversed、toSpliced（或先 [...arr] 复制）；看到数字排序必须确认显式传入了 (a, b) => a - b（升序）或 (a, b) => b - a（降序）。

方法论原则 12 · Clean Chains & Explicit Returns

核对数组方法语义是否匹配，盯紧 reduce 初始值与无 return 的花括号

AI 写长数组链时容易混用方法职责（用 map 干 filter 的活）、漏掉 reduce 的初始值导致空数组崩溃，或者在 reduce 里反复 { ...acc } 制造性能退化。

审阅动作：逐段对照职责：变换用 map、筛选用 filter、找单个用 find、判存在用 some；见到 reduce 先看有没有传第二个参数（初始值），再看累加器里有没有做 O(n²) 的 { ...acc } 展开；见到箭头函数右侧是 {，确认里面到底是要写函数体（有 return）还是返回对象字面量（应加 ({ ... })）。

四、实战演练：审阅一段 AI 写的订单汇总报表函数

假设你让 AI 写一个合并报表配置并计算头部订单统计的函数。下面这段代码在严格模式下完全可以通过 tsc --noEmit（零报错），但里面埋了 6 处典型问题（包含第 0 阶段强调的外部边界问题和本课全部三条原则）：

待审阅的 AI 交付物

order-report.ts
interface Order {
  id: number;
  customer: string;
  amount: number;
  paid: boolean;
}

interface ReportOptions {
  limit: number;
  filter: { minAmount: number };
}

const DEFAULT_OPTIONS: ReportOptions = {
  limit: 10,
  filter: { minAmount: 0 },
};

function buildOrderReport(orders: Order[], rawOverrideJson: string) {
  const override = JSON.parse(rawOverrideJson) as Partial<ReportOptions>;
  const opts = { ...override, ...DEFAULT_OPTIONS };
  opts.filter.minAmount = 100;

  const topOrders = orders
    .sort((a, b) => b.amount - a.amount)
    .slice(0, opts.limit);

  const paidNames = topOrders.map((o) => {
    if (o.paid) return o.customer;
  });

  const totalAmount = topOrders
    .filter((o) => o.paid)
    .map((o) => o.amount)
    .reduce((sum, n) => sum + n);

  return { opts, topOrders, paidNames, totalAmount };
}

按审阅清单逐行拆解（全部零编译报错，但运行时都有隐患）：

  1. 第 19 行（复习第 0 阶段边界检查）：JSON.parse(rawOverrideJson) as Partial<ReportOptions> 对外部 JSON 字符串直接裸用 as 断言，没有任何运行时结构校验。如果输入 JSON 损坏、是数组、或 limit 是字符串，脏数据会直接流入后续运算。
  2. 第 20 行（原则 10 · 覆盖顺序反了）：{ ...override, ...DEFAULT_OPTIONS } 把默认值放在了后面，用户传入的 limit 和 filter 会被 DEFAULT_OPTIONS 全部冲掉。应改为 { ...DEFAULT_OPTIONS, ...override }（且最好避免外部传入显式 undefined 键冲掉默认值）。
  3. 第 21 行（原则 10 · 浅拷贝污染全局常量）：即使顺序改对了，展开仍然是浅拷贝。当 override 未提供 filter 时，opts.filter 与模块级常量 DEFAULT_OPTIONS.filter 指向同一对象，执行 opts.filter.minAmount = 100 会永久污染全局默认配置，影响之后所有调用。应嵌套展开 filter: { ...DEFAULT_OPTIONS.filter, ...override.filter } 或先 structuredClone(DEFAULT_OPTIONS)。
  4. 第 24 行（原则 11 · 原地修改入参数组）：orders.sort(...) 直接原地打乱了调用方传入的 orders 数组。应改为 orders.toSorted((a, b) => b.amount - a.amount) 或 [...orders].sort(...)。
  5. 第 27–29 行（原则 12 · 误用 map 做筛选）：if (o.paid) return o.customer; 导致未付款订单产出 undefined，paidNames 实际类型是 (string | undefined)[]（用第 2 课的悬停一眼就能看到）。应先 .filter((o) => o.paid) 再 .map((o) => o.customer)。
  6. 第 34 行（原则 12 · reduce 漏传初始值）：当 topOrders 中没有已付款订单时，过滤后的数组为空 []，不传初始值的 reduce 会直接抛出 TypeError 崩溃。必须补上初始值 0（顺手还能合并第 31–34 行，减少一次多余的中间数组遍历）。

五、检验一下

本课自测（接续开头的 2 道热身题，全页共 8 题）。每题只能选一次，凭理解作答，不要往上翻。

执行 const copy = { ...base }; copy.nested.count = 9; 后，原对象 base.nested.count 会发生什么变化？

  1. 保持原值，展开语法会自动递归克隆全部嵌套属性
  2. 同步改变，展开只做浅拷贝，嵌套对象共享引用
  3. 变为缺失，展开语法在复制时会跳过所有嵌套属性
  4. 运行报错，展开产出的对象默认会锁定嵌套层写入
对象展开 { ...base } 永远只做一层浅拷贝：顶层基本类型互不影响，但嵌套对象属性只复制了引用地址，修改 copy.nested.count 会同步改掉 base.nested.count。需要隔离嵌套写入时应显式逐层展开或用 structuredClone。

执行 const { role = "guest" } = { role: null }; 后，变量 role 的值是什么？

  1. "guest"，解构默认值会同时处理 null 与 undefined
  2. undefined，解构赋值会把源对象中的 null 统一抹平
  3. 抛出异常，解构赋值不允许给已有 null 属性设默认值
  4. null，解构默认值只在目标属性为 undefined 时生效
与 ?? 不同，解构赋值的默认表达式只在属性值严格等于 undefined（或键不存在）时生效。遇到 null 时不会回退，变量 role 拿到的就是 null。若需同时兜底 null，解构后再配合 ?? 使用。

对数组 const nums = [10, 2, 1]; 调用 const res = nums.sort(); 后，下面哪项描述正确？

  1. 原数组保持不变，结果按数值升序排为 [1, 2, 10]
  2. 原数组被原地修改，结果按数值升序排为 [1, 2, 10]
  3. 原数组被原地修改，默认按字符串序排为 [1, 10, 2]
  4. 原数组保持不变，默认按字符串序排为 [1, 10, 2]
Array.prototype.sort() 有两个经典坑：第一，它会直接原地修改原数组（返回的就是原数组引用）；第二，不传比较函数时会把元素转成字符串按 UTF-16 码元顺序排，所以 "10" 排在 "2" 前面。数值安全排序应写 nums.toSorted((a, b) => a - b)。

想用调用方传入的 override 覆盖默认配置 defaults，且强制把结果里的 role 锁定为 "user"，哪种展开顺序正确？

  1. { ...defaults, ...override, role: "user" }
  2. { role: "user", ...defaults, ...override }
  3. { ...override, ...defaults, role: "user" }
  4. { role: "user", ...override, ...defaults }
对象展开按从左到右的顺序写入，靠后的同名属性会覆盖靠前的。因此基础默认值 ...defaults 放最前，允许覆盖的 ...override 放中间，需要强制锁定的 role: "user" 放最后，防止被外部传入的同名字段越权覆盖。

AI 写了 const ids = users.map(u => { id: u.id });，意图把用户数组映射成 { id } 对象数组。实际运行结果是什么？

  1. 返回正常的 { id } 对象数组，语法会自动识别对象字面量
  2. 编译阶段直接报错，箭头函数体内部不允许出现冒号表达式
  3. 过滤掉所有元素返回空数组，对象字面量被判定为假值跳过
  4. 返回全是 undefined 的数组，花括号被当成无返回的函数体
箭头函数右侧紧跟 { 时会被解析为函数代码块而非对象字面量，id: 会被当成语句标签且没有 return，每次回调都返回 undefined。箭头函数简写返回对象必须加圆括号：u => ({ id: u.id })。

AI 写了 orders.filter(o => o.paid).map(o => o.amount).reduce((a, b) => a + b) 汇总已付金额，为什么审阅时必须要求补上初始值 0？

  1. 不传初始值会把首个元素当字符串拼接，导致结果类型变成文本
  2. 过滤后若为空数组，不传初始值的归约会直接抛出运行时类型错
  3. 不传初始值会触发延迟求值机制，导致前面的过滤步骤被直接跳过
  4. 过滤后若仅有一项，不传初始值会跳过该项并固定返回未定义的值
不传 initialValue 时，reduce 会尝试取数组第一个元素作为累加器初值。一旦 filter 过滤后得到空数组 []，运行时会立刻抛出 TypeError: Reduce of empty array with no initial value。此外补上初始值也能明确累加器类型，防止归约对象数组时首项类型不匹配。
